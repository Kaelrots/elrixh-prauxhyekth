# 은하·행성 지도 에디터 EXE 전환 — 공통 실행 기준

버전: 1.0 · 작성일: 2026-10-02 · 용도: WORK/Codex 구현 인계
상태: <font style="font-weight:bold">계획서 작성 완료 / 전환 구현·실행·빌드 미실시</font>

## 1. 목표와 문서 사용법

기존 화면·도메인·파일 호환성을 보존하면서 두 편집기를 <font style="font-weight:bold">개발 서버나 별도 Node 설치 없이 실행하는 Windows 데스크톱 앱</font>으로 제공한다. 도시 편집기의 실행·저장·복구·검사·배포 절차를 재사용하되, 제품 데이터 검증과 렌더링은 각 앱의 계약을 유지한다. ‘EXE 파일 하나 생성’을 완료 기준으로 삼지 않는다. [R0 §§1–4]

읽는 순서: `05_사전조사_근거와미확인사항.md` → 이 문서 → 해당 제품 계획서 → 해당 단계의 검증표. 작업 중에는 제품별 `DESKTOP_MIGRATION_STATE.md`와 변경 목록을 우선 읽는다. 이 묶음의 R/G/P/W 근거 ID는 모두 05 문서에서 정의한다.

아래의 단계, 작업 ID, 증거 파일명, 저장 응답 계약, 완료 등급은 <font style="font-weight:bold">이번 계획의 실행 제안</font>이다. 실제 모듈명·버전·사용자 로컬 경로가 이미 그렇게 되어 있다는 뜻이 아니다.

## 7. 저장 요청과 응답 — 새 실행 계약

### 7.1 권한과 데이터 외피

화면에 일반 `fs`, 임의 shell, 임의 경로 읽기·쓰기를 노출하지 않는다. 파일 대화상자 또는 앱이 승인한 경로에서만 열기·저장·내보내기를 실행한다. 요청에는 `requestId`, renderer 세대, 프로젝트 식별, 현재 revision, 저장할 snapshot 식별/해시를 연결한다. 이것은 데스크톱 관리 정보이며 기존 core 스키마에 무단 주입하지 않는다.

응답에는 성공/취소/실패, 실제 저장한 snapshot, 실제 경로, 검증 결과, 복구 세대·사유를 담는다. 숫자 revision만 비교하지 않는다. 분기된 사본은 같은 revision이어도 내용이 다를 수 있으므로 내용 해시·기준 부모 정보를 함께 비교한다.

### 7.2 상태 전이

`변경 없음 → 미저장 → 준비/검증 → 기록 → 게시/완료 확인 → 해당 snapshot 저장됨`을 기본으로 한다. 취소·실패·충돌은 별도 상태다. 저장 중 새 편집이 생기면 완료 응답은 저장했던 옛 snapshot에만 적용한다. 현재 상태와 다르면 ‘추가 변경 미저장’을 유지한다.

프로젝트별 디스크 commit은 직렬화한다. 자동 저장 대기열은 최신 대기로 합칠 수 있으나 명시적 저장 요청을 말없이 버리지 않는다. 같은 요청 재전달·renderer 교체·Worker 재시작·늦은 응답이 다른 문서 상태를 바꾸지 않아야 한다.

### 7.3 실제 파일 쓰기

기본 순서는 `이전 정상본 유지 → 같은 볼륨의 임시 기록 → 파일 동기화 → 재읽기·검증 → 완성 세대 게시 → 최신 안내 갱신`이다. 최종 경로 교체 실패 시 이전 정상본을 지키고 실패를 알린다. 임시 기록·게시·안내 갱신 어느 단계에서 실패했는지 구별한다. Windows 잠금과 정전 내구성은 실제 환경 확인 없이 완전 보장하지 않는다. [R0 §8]

여러 자산 파일을 포함하면 완성된 세대 디렉터리·manifest를 단위로 게시한다. 모든 파일이 존재·검증되기 전에 최신 포인터를 바꾸지 않는다. 사용자의 프로젝트 파일 덮어쓰기는 명시적으로 선택한 저장 대상에 한하며, 외부 변경을 감지하면 사본 저장·비교를 제시하고 자동 덮어쓰기하지 않는다.

### 7.4 열기와 복구

열기는 <font style="font-weight:bold">후보 상태 구성 → 전체 검증 → 현재 프로젝트 교체</font> 순서다. 손상 파일을 읽다가 현재 작업 일부만 바꾸지 않는다. 검증은 바이트 무결성뿐 아니라 스키마·ID·참조·기하·필수 자산을 포함한다. 이전 정상 세대로 돌아가면 원래 최신 revision과 복구 revision, 잃을 수 있는 변경 범위·사유를 표시한다.

의미 오류가 있는 최신본에서 이전 세대를 찾는 정책은 명시적으로 결정한다. 기본 제안은 같은 프로젝트의 후보를 최신순으로 <font style="font-weight:bold">전체 검증</font>해 정상본을 제시하고, 손상본은 보존하며, 사용자에게 이전 시점 사용을 알리는 것이다. 정상본이 없으면 현재 프로젝트를 유지한다. 미래 포맷·자산 누락을 ‘빈 프로젝트’로 대체하지 않는다.

### 7.5 저장 종료와 버리기

종료 시 ‘저장 후 종료 / 변경 버리기 / 취소’를 구분한다. 저장 실패 시 창을 닫지 않는다. 폼에만 있는 초안과 적용된 편집을 구분해 알린다. 강제 종료는 정상 종료와 별도 검사한다. ‘버리기’를 누른 변경을 다음 실행에서 최신 작업처럼 자동 부활시키지 않도록 세션의 복구 정책을 정의하되, 과거 정상 복구본 전체를 지우지 않는다.

### 7.6 네이티브 저장과 다운로드 경로

데스크톱 프로젝트 저장은 네이티브 대화상자·저장 서비스의 실제 commit 완료를 기준으로 한다. 기존 PNG/CSV 등 다운로드 경로를 유지하는 경우에만 Electron `will-download`/`DownloadItem` 완료·취소·중단과 실제 파일을 검사한다. 모든 저장을 웹의 다운로드 이벤트로 검증하거나, 모든 다운로드가 실패한다고 가정하지 않는다. [R0 §5]

## 8. 브라우저 복구본 이관과 자산 관리

Chrome/Edge의 기존 IndexedDB가 Electron에 자동 승계된다고 가정하지 않는다. 원래 브라우저·프로필·주소/포트에서 중요 프로젝트와 복구본을 파일로 내보내고, 네이티브 앱에서 읽어 비교한다. 원래 프로필 DB를 직접 긁거나 옮기는 방식은 기본 범위에서 제외한다. 기존 웹 실행본과 원본 복구 데이터는 남긴다. [R0 §§3·8, G3]

로컬 자동 복구, 수동 백업, 전달 사본, 재생성 가능 캐시를 별개로 보관한다. 크기 예산을 초과해도 최신 정상본과 사용 중인 자산을 우선 지키며 실패 원인을 표시한다. 복구 세대의 참조가 남아 있는 자산을 캐시 청소로 삭제하지 않는다. 복구 보존 개수와 바이트 예산은 제품별 표본으로 결정한다.

압축 파일은 압축 바이트·해제 총량·파일 수·단일 항목 크기·경로를 각각 검증한다. 경로 탈출·중복 경로·허용하지 않은 링크·과도한 중첩을 거부한다. 선택적 그림 누락은 명시적 제한 상태로 열 수 있지만 필수 식별 자산 누락을 완전 복원으로 표시하지 않는다.

## 9. 보안과 배포 기본값

`nodeIntegration: false`, context isolation·sandbox 유지, 좁은 context bridge와 IPC 발신자 검증을 기본으로 한다. 임의 navigation·새 창·외부 protocol은 제한한다. 사용자 Markdown/CSV/프로젝트의 스크립트를 실행하지 않는다. 도시의 `unsafe-eval` 같은 예외를 근거 없이 복사하지 않는다. [R0 §8, W1]

기본 배포물은 소스의 개인 `reference/` 자료를 자동 포함하지 않는다. 오프라인 요구에 필요한 앱 자산·Worker·허가된 예제만 포함한다. 의존성·라이선스 고지와 서명 상태를 기록한다. 서명 인증서가 없으면 미서명이라고 표시하고 시스템 보안 기능을 끄게 하지 않는다. 자동 업데이트·파일 연결·시작 프로그램 등록은 별도 요구가 없으면 기본 전환에서 제외한다. [W4–W5]

## 11. 성능 계획과 재검사 정책

작은 정상 확인 → 이상 원인 판별 → 대표 부하 순서다. 같은 실패가 반복되면 동일 조건의 무의미한 재실행을 멈추고 ‘입력/권한/자산/앱 처리/자동화 대기’ 중 가설 하나를 판별한다. timeout 값을 키우거나 sandbox를 끄는 것을 해결책으로 삼지 않는다. [R0 §§5·7·10]

기존 웹·변경 웹·EXE는 같은 입력 해시, 동일 작업 순서, 뷰포트, 창 표시/포커스, PC 조건으로 비교한다. 콜드/웜을 나누고 초기 대표 조건은 각 3회로 시작한다. 3회 결과를 p95라 부르지 않는다. 앱 내부 처리·사용자 완료 체감·도구 대기를 구별하고 프로세스별 메모리·GPU/캐시를 가능한 범위에서 기록한다. Playwright 이상값은 공개 UI와 내부 시각으로 대조한다. [W3]

성능 판정값은 B 단계에서 현행 승인 목표와 실제 PC를 근거로 고정한다. 없는 목표는 측정 후 제안하되 개선율을 미리 보장하지 않는다. 불가피한 Electron 기본 메모리 증가와 데이터 크기에 비례하는 누수는 구분한다. 최적화는 결과가 나빠지면 해당 변경만 되돌린다.

## 12. 빌드 출처와 배포 세대

F 시작 시 소스 스냅샷을 고정한다. commit SHA만으로 미커밋 변경까지 포함되었다고 주장하지 말고 실제 빌드 입력 목록·SHA-256, lockfile·설정·도구 버전·자산을 기록한다. 빌드 전후 입력 변화를 감지하면 해당 빌드를 최종본으로 게시하지 않는다.

`소스 입력 manifest → 실제 빌드 자산 해시 → 패키지 내부/외부 자산 대조 → EXE/설치본 해시 → 실제 실행 결과`를 연결한다. 이는 빌드 출처 추적이며 바이트 단위 재현 가능한 빌드를 자동 보장하는 것은 아니다. ASAR 외부의 Worker·네이티브 모듈·폰트·타일 자산도 배포 구조에 따라 확인한다. [R0 §11]

새 배포는 고유 generation 폴더에 만든다. 동기화 폴더의 사용 중인 디렉터리나 이전 정상 EXE를 덮어쓰지 않는다. 무설치 폴더 검사 후 설치본을 만들고, 최상위 실행 안내·해당 PC 바로가기 대상을 다시 확인한다. EXE 하나만 복사하라고 안내하지 않는다. `.lnk` 절대경로가 다른 PC에서도 유효하다고 가정하지 않는다.

## 13. 두 PC·Drive·Git 인수

1. PC-A에서 프로젝트 편집 → 전체 자산을 갖춘 전달 사본 생성 → project ID/revision/hash/부모 해시 기록.
2. 고유 이름으로 Drive에 전달 → 실제 업로드 완료 확인. 코드 push와 구분한다.
3. PC-B에서 다운로드 완료·해시 검증 → 오프라인 열기 → 데이터·자산·보기 상태 확인 → 한 번 편집·저장.
4. B의 새 전달 사본을 Drive로 반환 → A에서 검증·재열기 → 동일 변경과 원래 데이터 보존 확인.

한 시점에 한 PC를 편집자로 운영한다. 동시 분기는 보존하고 자동 병합하지 않는다. 폴더 잠금 파일만으로 Drive를 통한 분산 잠금이 보장된다고 설명하지 않는다. 프로필/캐시는 기기마다 로컬이며, 전달본은 이와 독립적으로 재열려야 한다. [R0 §8]

설치·제거는 허용된 사용자 계정 또는 격리된 시험 환경에서 수행한다. 제거 때 사용자 프로젝트가 삭제되지 않아야 한다. 다른 앱의 프로필/확장자/바로가기를 덮어쓰지 않는다. push·병합·공개 배포는 실제 실행 지시가 허용할 때만 수행하며 이 계획서가 외부 변경의 포괄적 권한을 부여하지 않는다.

## 14. 실패 분류와 인계

검사 상태는 `NOT_RUN / PASS / FAIL / BLOCKED_INPUT / BLOCKED_ENVIRONMENT / NOT_APPLICABLE`로 기록한다. N/A는 기능·플랫폼상 적용되지 않는 근거가 있어야 하며 미구현 필수 기능을 N/A로 숨기지 않는다. 실패마다 증상·재현 입력·확인 원인과 가설·수정 범위·재검사 근거를 남긴다.

각 앱의 마지막 보고는 현재 등급, 실제 실행 경로, 마지막 통과 관문, 미완료 항목, 데이터 보존 결과, 성능과 한계, 설치/서명, Git/Drive/두 PC 각각의 상태, 다음 작업 1개를 포함한다. 정상 로그 전문이나 세계관 JSON 전체를 대화에 붙이지 않는다. 실제 토큰 기록이 없으면 절감률을 만들어내지 않는다.
