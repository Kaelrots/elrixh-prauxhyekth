표준 문서(규칙·사전)

이 문서는 테크트리 문서군의 단일 기준(Single Source of Truth) 입니다.
개별 시대/게이트/엣지 문서는 본 규칙을 참조하며, 규칙과 충돌 시 본 문서가 우선합니다.

상세 수정 내역

  • 90-기타 문서 기본 템플릿
  • 문서수정기록 파일링크

0. 목적

  • 본 문서는 제2기 이후 기술·연구 테크트리를 “시대별 게이트(노드) + 선후관계(엣지)”로 운영하기 위한 서술 규칙/표준/사전이다.
  • 목표:
  • (1) 문서량이 증가해도 ID·표기·분류·관계가 흔들리지 않게 한다.
  • (2) A → B 선후관계로 트리/그래프를 생성할 수 있게 한다.
  • (3) 시대 인덱스(목차)와 게이트 노드(본문)를 분리해 중복/충돌을 방지한다.

작업 프로세스(표준)

문서 역할(SSOT)

  • 10-01 시대 인덱스: 시대별 “게이트 목록/발급대장” (gate_id 발급은 여기서 선확정)
  • 10-02 게이트 노드: 게이트 1개 설명(왜 게이트인가/매핑/요약/연계)
  • 10-03 엣지 레지스트리: 관계(선후/배타/대체)의 단일 기준(SSOT)
  • 10-04 상세 기술(선택): 세계관 핵심 기술만 백과사전급으로 분기

0-1. 표준 워크플로우(권장 순서)

  1. 시대 정의(시대 문서)
    • 시대 경계(기간) + 변곡점 축(생산/군사/통치/차원/대외)만 먼저 확정
  2. 10-01 시대 인덱스 작성(게이트 목록/발급)
    • gate_id 발급(불변) + 인링크 골격
    • 최소 기입: tree_map, sub_type(공통12), TMC(·CODE 허용), 한 줄 효과, Ref 키워드
  3. 10-02 게이트 노드 생성(코어부터)
    • 최소 스키마(YAML) + “왜 게이트인가” + 매핑 근거
    • 중요 기술만 detail_doc로 10-04 상세 기술 분기
  4. 10-03 엣지 레지스트리 작성(관계 원장)
    • 시대 내부(로컬) → 교차시대(점프) 순
    • 교차시대 엣지는 note 1줄 이상 필수
  5. (선택) 검증/시각화 출력(코딩 영역)
    • 10-03을 입력으로 그래프 생성/사이클/중복/누락 자동검증

0-2. 작업 단위(추천: “코어 8개” 루프)

  • ① 인덱스에 코어 8개 채움 → ② 노드 8개 생성 → ③ 엣지로 뼈대(10~30개) 잡기
  • 이후 “확장 후보”를 12~22개로 늘리면서 ①②③을 반복(얇게 순환)

0-3. 변경/유지보수 규칙(필수)

  • gate_id는 발급 후 불변(이름/설명은 바뀌어도 됨)
  • 관계 충돌 시 우선순위:
    1. 10-03 엣지 레지스트리
    2. 10-02 게이트 노드(설명/맥락)
    3. 10-01 인덱스(목록)
  • 삭제 대신 status: deprecated로 폐기(관계/노드 추적성 유지)
  • 시대 점프(교차시대) 엣지는 근거(note/source) 없는 채로 금지

0-4. 빠른 품질 점검(체크리스트)

  • 10-01의 gate_id와 10-02/10-03의 ID가 1:1로 대응
  • 모든 노드에 tree_map ≥ 1, sub_type 1개 지정
  • 교차시대 엣지에 note 존재
  • alt_path와 mutex 혼용 없음
  • 의도치 않은 사이클(특히 prereq_hard) 없음

1. 적용 범위 및 전제

1-1. 적용 범위

  • 적용 기수: 제2기 이후
  • 적용 대상 문서군:
  • 시대 인덱스 문서(게이트 목록)
  • 게이트 노드 하위문서
  • 엣지 레지스트리(관계 표)
  • (선택) 트리 시각화/검증 문서

1-2. 우선순위

  • (1) 본 문서(규칙·사전)
  • (2) 제2기 연구트리 분류체계(3단계) 정의 문서
  • (3) 시대/게이트/엣지 개별 문서

2. 문서 유형(doc_type) 정의

2-1. doc_type 목록

  • tech_tree_rules: 본 문서(규칙)
  • era_gate_index: 시대 인덱스(시대별 게이트 표)
  • gate_node: 게이트 노드(단일 진실)
  • gate_edges: 엣지 레지스트리(관계 표)
  • (선택) gate_tree_view: 트리 시각화/검증(mermaid/필터/레이어)

2-2. 역할 분리 원칙

  • 시대 문서(인덱스): 얇게(표/요약/링크만)
  • 게이트 문서(노드): 두껍게(정의/근거/관계/연계)
  • 엣지 문서(관계): 관계만(표 중심)

금지

시대 인덱스 문서에 “관계 본문”을 길게 적지 않는다.
게이트 노드 문서에 “전역 관계표”를 복붙하지 않는다.

3. 식별자(Identifier) 규칙

3-1. 시대 코드(era)

  • 형식: 2-01, 2-02, … 2-99
  • 의미: 2기-시대번호
  • 예시: 2-03 = 제2기 03시대

3-2. 게이트 ID(gate_id)

  • 형식: G2-<era>-<nnn>
  • <era>: 01～99 (시대번호 2자리)
  • <nnn>: 001～999 (3자리 연번)
  • 예시:
  • G2-03-001
  • G2-03-014

3-3. 표 No(번호) 원칙

  • 시대 인덱스 표의 No는 보기용이다.
  • 게이트를 추가/삭제하며 번호가 변경되어도 gate_id는 절대 변경하지 않는다.

3-4. 이름(게이트명) 원칙

  • 게이트명은 바뀔 수 있다(명칭 개편/번역 수정 등).
  • 그러나 링크/관계/키는 항상 gate_id를 기준으로 한다.

불변 규칙

gate_id는 한 번 발급하면 영구 불변이다.

4. TMC(성숙도·단계) 표기 규칙

4-1. 기본 형식

  • 형식: <ERA>-<TRL>
  • ERA(시대축): ANC / MED / EMO / IND / MOD / NFU / FUT / SPC
  • TRL(성숙도): 1～9

4-2. 기간/범위 표기

  • 범위형: MOD-7～9 처럼 표기한다.
  • 문서 전체에서 ~는 사용하지 않고 ～ 로 통일한다.

4-3. (선택) 특수 코드(Special Code)

  • 특수 코드는 ·로 결합한다.
  • 표기 권장: <ERA>-<TRL>·CODE
    • CODE: LST / ARC / TRN
  • 예시:
    • MOD-7～9·LST (현대 후기급으로 ‘추정’되나 전승 단절)
    • NFU-5·ARC (근미래 중기급 + 신비)
    • SPC-2·TRN (우주 시대 분류 + 초월)
  • 주의: “실전”은 실전(實戰)이 아니라 실전(失傳) 의미로 사용한다.

5. 특수 코드(Special Code) 사전

특수 코드는 선택 사항이다. 쓰려면 아래 정의를 따른다.

CODE의미사용 기준(권장)
`LST`실전/失傳 기술존재 증거는 있으나, 표준/매뉴얼/교육체계 붕괴로 “재현 가능한 지식”으로 전승되지 못한 기술
`ARC`신비 기술원리 불명/가설 난립, 재현성 낮음, 이능·차원·종교/신성 요소와 구조적으로 강결합
`TRN`초월 기술현 체계로 해석·역공학·재현 루프가 성립하지 않는 블랙박스 기술

운영 원칙

  • 남발 금지. ‘게이트의 본질’이 명확할 때만 붙인다.
  • ARC + TRN은 원칙적으로 배타적: TRN 판정이면 ARC를 생략해도 된다(초월이 상위 개념).
  • 표기: 기술 수준: <ERA>-<TRL>·CODE

6. 연구트리 3단계 매핑 규칙(tree_map)

6-0. 세부 유형(sub_type) 전제(공통 12종)

  • 세부 유형은 트리마다 따로 만들지 않고, 공통 12종으로 통일한다.
  • 원칙: 노드는 트랙(3단계) + 세부유형(1～12) 조합으로 구성된다.
  • 공통 12종:
    1. 이론/원리
    2. 계측/표준
    3. 공정/제조
    4. 인프라/네트워크
    5. 제도/법규
    6. 조직/운영
    7. 종교교리/규범
    8. 군사교리/훈련
    9. 통제/보안
    10. 대외/접촉
    11. 시험/검증(V&V)
    12. 모델/시뮬레이션/소프트웨어(SIM)
  • 표기(권장): sub_type: "<번호>. <이름>" (예: sub_type: "2. 계측/표준")

6-1. 매핑 필수

  • 모든 gate_node는 최소 1개의 3단계 매핑을 가져야 한다.
  • 시대 인덱스(era_gate_index)에도 동일 매핑을 요약 기입한다.

6-2. 복수 매핑 허용 기준

  • 복수 매핑은 허용하되, 아래 중 하나를 충족해야 한다:
  • (A) 하나의 게이트가 실제로 2개 이상의 분야를 동시에 개방한다.
  • (B) ‘핵심 매핑 1개 + 보조 매핑 1개’로 설명 가능하다.

6-3. 표기 형식

  • 표기: 3-XX → (하위 트랙명)
  • 복수 매핑 시: 줄바꿈/리스트로 나열

6-4. 매핑 검증 원칙

  • 존재하지 않는 3-XX 코드를 임의로 사용하지 않는다.
  • 애매하면, 게이트 노드 문서의 “매핑 근거”에 왜 그 트랙인지 2～5줄로 명시한다.

7. 선후관계(Edge) 규칙

7-1. 관계의 단일 키

  • 관계는 항상 gate_id로만 표현한다.
  • 게이트명으로 관계를 정의하지 않는다.

7-2. Hard/Soft 선행조건

  • Hard: 없으면 절대 성립/운용이 불가능한 선행
  • Soft: 강하게 권장되나, 우회/대체 경로가 가능한 선행

7-3. 엣지 레지스트리(rel_type) 사전

rel_type의미사용 예
`prereq_hard`필수 선행제도/인프라가 없으면 기술이 불가능
`prereq_soft`권장 선행효율/확산을 위해 필요, 우회 가능
`alt_path`대체 경로(동등)A 루트 또는 B 루트 중 하나로 도달
`synergy`시너지둘 다 있으면 성능/파급이 증가
`obsoletes`사실상 대체/구식화상위 기술이 하위 기술을 흡수
`mutex`상호배타같은 슬롯(교리/제도)에서 동시 불가

7-4. weight 규칙(선택)

  • weight는 0.0～1.0 사이로 둔다.
  • 1.0 = 거의 필수 수준
  • 0.6 = 강한 권장
  • 0.3 = 느슨한 연계

7-5. 시대 점프 엣지

  • 2-01 → 2-04처럼 시대를 크게 건너뛰는 엣지는 허용하되,
  • 엣지 레지스트리의 note에 왜 점프하는지 반드시 1줄 이상 적는다.

7-6. 사이클(순환) 규칙

  • 의도치 않은 사이클은 금지.
  • 의도된 순환(상호강화 루프)을 표현해야 한다면:
  • synergy로 표현하고,
  • prereq_*로 사이클을 만들지 않는다.

8. 문서별 필수 요소(최소 스키마)

8-1. 시대 인덱스(era_gate_index)

  • 반드시 포함:
  • 시대 코드(era), 시대명(era_name)
  • 게이트 표(최소 core 8개)
  • 각 행에: gate_id, 인링크, tree_map, TMC, 한줄 효과

8-2. 게이트 노드(gate_node)

  • 반드시 포함:
  • gate_id, gate_name, era, tmc, tree_map
  • prereq.hard[], prereq.soft[], unlocks[] (없으면 빈 배열)
  • 본문 섹션: 개요 / 왜 게이트인가 / 매핑 근거 / 선행 / 후속

8-3. 엣지 레지스트리(gate_edges)

  • 반드시 포함:
  • from_gate, to_gate, rel_type
  • (권장) weight, note

9. 금지·권장 규칙

9-1. 금지

  • gate_id 재사용/재발급(중복) 금지
  • 게이트명을 키로 삼는 관계 정의 금지
  • 시대 인덱스에 관계 본문을 길게 서술 금지
  • 존재하지 않는 3단계 코드 임의 생성 금지

9-2. 권장

  • 게이트 노드에는 “경계선(포함/비포함)”을 1줄이라도 적기
  • 시대 점프 엣지는 반드시 note로 설명
  • 오버레이는 정말 필요할 때만

10. 품질 점검 체크리스트

10-1. 신규 게이트 추가 시

  • gate_id 유일성 확인
  • 시대 인덱스 표에 gate_id + 인링크 반영
  • gate_node에 tree_map 최소 1개 존재
  • prereq/unlocks가 있으면 엣지 레지스트리에도 반영
  • “왜 게이트인가”가 시대 변곡점과 연결되어 있음

10-2. 트리(관계) 점검

  • 의도치 않은 사이클 없음
  • 허브 과집중(병목)이 의도인지 확인
  • 시대 점프 엣지에 note 존재
  • mutex/alt_path를 혼동하지 않음

11. 변경·버전 관리 규칙

  • 본 문서의 변경은 문서버전을 올리고, 최근 변경 요약에 1줄 기록한다.
  • 규칙 변경이 개별 문서에 영향을 줄 경우:
  • (권장) “영향 범위(예: 게이트 노드 전체)”를 변경 요약에 함께 적는다.

  • G2-03-001 (Soft) → G2-04-003
